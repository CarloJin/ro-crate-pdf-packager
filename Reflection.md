# Reflection

I spent a little over ten minutes writing the initial SPEC before asking the assistant to generate code. That was a substantial part of a 60-minute exercise, but I wanted to settle the main decisions before implementation. I defined the workflow, metadata fields, module responsibilities, crate structure and checks. I also specified how to handle missing metadata, keep user edits and preserve the original PDFs. I think this time was well spent. The assistant stayed close to the requirements, and the only implementation error I encountered was a browser compatibility issue.

I used six stages: write the SPEC; check the environment and library APIs; build the complete MVP; test it in the browser and fix the failure; check the actual exported crate; then freeze features and prepare the submission. I asked for a brief integration check before the build, including a real PDF.js worker and basic RO-Crate creation. Each prompt gave the assistant a clear task, checks and a stopping point. After implementation, I explicitly asked it to stop so I could try the app myself.

I chose Vite and Node.js tooling because the task required JavaScript and npm libraries. Vite gave me a development server, a production build and a way to bundle the PDF.js worker. Node was only needed for development and tests; the app processed files in the browser. Plain HTML and JavaScript were enough for this interface. Separate modules for file access, extraction, crate construction and the UI made the code easier to review and test. Browser directory handles let users choose an output directory, but limited the target to desktop Chrome/Edge on localhost or HTTPS.

I chose `pdfjs-dist` because it could read both PDF information fields and XMP metadata and run with a browser worker. This suited the supplied files with inconsistent metadata. I did not need to write a parser or modify the PDFs. I asked the assistant to check the installed APIs rather than guess method names. This also identified the RO-Crate library's default version of 1.2 before implementation, so the app explicitly configured 1.3. I did not encounter fabricated output, such as invented library methods. The browser failure involved a real API that was unavailable in that browser, not an invented one.

I kept “Extracted creation date” non-editable because it showed what was read from the PDF. It might be the date software created the file, which is different from publication. Users could enter a separate publication date. The extracted date could still be wrong. A future version could allow a correction while keeping the original value and recording who changed it.

In my browser test, extraction failed with `this[#methodPromises].getOrInsertComputed is not a function`, although it worked in Chrome. The assistant's initial check had passed in its test browser and missed this compatibility problem. I asked it to inspect the installed source and reproduce the error. PDF.js 6.3.289 called a newer Map method; disabling that method reproduced the failure. I requested the smallest fix: pin a compatible PDF.js version and keep the main module and worker versions matched. Version 5.4.624 passed the regression, extraction and build checks. I then asked for the constraint to be added to SPEC. The simulation did not replace a check in the affected browser. Next time, I would test in the browser intended for the demonstration during setup.

I prioritised a complete MVP and excluded all stretch goals: checksum metadata, ORCID, full automated validation and a static preview. I reserved the remaining time for manual review, verification and submission work, and did not attempt them. Hashes were used to check copied files, but were not added to crate metadata. My actual eight-file export passed focused checks of the RO-Crate structure, references, paths and unchanged PDF bytes. This was not full conformance validation. The export contained no author links or nested duplicate filenames, and the checks could not independently confirm every value against my earlier browser input. With more time, I would cover these cases, permission failures and write errors before adding features.

My usual PRD process is compound engineering: Brainstorm → Plan → Work → Review → Compound → Repeat. Our team already keeps the PRD synchronised. The useful difference here was writing down assumptions that colleagues might share but an AI assistant would not know, such as date meanings and how to handle empty fields. The SPEC gave the assistant concrete instructions and gave me something to check its work against. It reduced the need to repeat decisions across prompts. Adding the compatibility lesson also fitted the Compound step. However, a wrong SPEC could lead the assistant to build the wrong thing consistently. I still needed to question the design and test it.

I support AI coding. It helped me implement the workflow quickly, inspect unfamiliar APIs and produce tests and useful error evidence. It also handled repetitive code. My responsibility was to set priorities and decide whether its results were sufficient. The browser issue reminded me that passing tests only covered the environment we had checked. I still needed to test the app myself. I also need to understand the generated code well enough to maintain it, update dependencies and fix later problems.

For LDaCA Language Research Technology projects, I would agree on AI boundaries with the relevant communities and data custodians before giving an assistant access to Indigenous language materials. This includes what it can read, where processing happens and what is retained. Synthetic test data could support development without exposing restricted recordings or transcripts. Browser-local processing does not control a coding assistant's file access. Also, a valid RO-Crate and a completed licence field do not establish permission to publish. AI can miss cultural context or suggest unsupported language labels and attribution. Those decisions need review by people with the knowledge and authority to make them.
